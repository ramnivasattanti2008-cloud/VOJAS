## Health Checks

### Endpoints

| Endpoint | Auth | Purpose | DB Check |
|----------|------|---------|----------|
| `GET /health` | None | Liveness — process up. Safe for k8s livenessProbe / Render health check. | No |
| `GET /ready` | None | Readiness — process is up AND database is reachable. Safe for k8s readinessProbe / load balancer. | Yes (`SELECT COUNT(*) FROM projects`) |
| `GET /api/v1/health` | None | Smoke-test compat. Returns DB-reachable / degraded / DB_TIMEOUT (2s ceiling). | Yes (bounded 2s) |
| `GET /api/v1/ready` | None | Extended readiness with response time. | Yes |

### Behaviour

- **Liveness (`/health`)** — returns 200 instantly. Used by orchestrators to detect a hung process. Does NOT touch the database (so a slow DB does not cause cascading restarts).
- **Readiness (`/ready`, `/api/v1/ready`)** — runs `prisma.project.count()` or `SELECT 1` and reports response time. Returns 503 if the database is unreachable so load balancers can drain traffic.
- **Bounded timeout** — `/api/v1/health` has a 2-second timeout. If the DB doesn't respond in time, the endpoint reports `DB_TIMEOUT` (503) instead of hanging.

### Admin Health Page
`/admin/health` shows real-time health for:
- Database connectivity
- API server
- Satellite provider
- Map services
- AI services
- Storage
- Job queue
- Authentication

Uses `useHealthStatus` and `useHealthHistory` hooks (React Query, 60s refetch).

## Observability

### Request Tracing

Every incoming HTTP request gets a UUID v4 `requestId`:
- Generated by `requestIdMiddleware` in `apps/api/src/middleware/observability.ts`
- Echoed in the `X-Request-Id` response header (so clients can include it in bug reports)
- Honored if client passes a safe `X-Request-Id` header (regex-validated to prevent log injection)
- Attached to `req.requestId` and `req.startedAt` for downstream middleware
- Returned in every error response: `{ success: false, requestId, error: { ... } }`

### Structured Logging

All logs go through `apps/api/src/utils/logger.ts`:
- **Production**: single-line JSON: `{ ts, level, msg, requestId, method, path, status, durationMs, ... }`
- **Development**: pretty-printed with color-coded levels
- **Levels**: `info` (2xx), `warn` (4xx, AppError, Prisma), `error` (5xx, unhandled)
- **Child loggers**: `logger.withContext({ requestId, userId })` returns a pre-bound logger

### Sensitive Field Redaction

The `redactForLog` function (used in error handler + observability middleware) recursively strips:
- `password`, `passwordHash`
- `token`, `accessToken`, `refreshToken`
- `sessionId`
- `secret`, `apiKey`
- `authorization`, `cookie`
- `whistleblowerToken`, `accessTokenExp`, `refreshTokenHash`

Truncates string values > 500 chars; depth-limits object recursion at 4 levels.

### What Is Logged
- HTTP method, path, status, duration (every request — `requestLogger`)
- requestId, userId (when authenticated)
- DB connection / disconnection (lifecycle)
- Satellite job lifecycle: `enqueue`, `running`, `retry #N`, `completed`, `failed`
- CDSE token acquisition, STAC search errors
- Health-check failures
- AppError subclasses (warn level — expected errors)
- Unhandled errors (error level — full stack in dev only)

### What Is NOT Logged
- Passwords, tokens, secrets, PII (redacted or omitted)
- Request bodies (only logged at debug level, after redaction)
- Successful satellite scene payloads (only counts)
- Full observation data

## Error Handling

### Error Flow
1. Route handler throws an `AppError` (or unknown `Error`)
2. Express forwards to `globalErrorHandler` via `next(err)`
3. Handler classifies error:
   - `AppError` → returns its `statusCode`, `code`, `message`, optional `details`
   - Prisma error (`Pxxxx`) → returns 400/404 with safe generic message
   - Anything else → returns 500 `INTERNAL_ERROR`, full detail logged server-side

### Never Exposed to Client
- Stack traces (only in dev `console.error`)
- Internal file paths
- Database structure / column names
- Environment variables
- Other users' data

### Standard Error Shape
```json
{
  "success": false,
  "requestId": "abc-123-...",
  "error": {
    "code": "NOT_FOUND",
    "message": "Project not found"
  }
}
```

For validation errors:
```json
{
  "success": false,
  "requestId": "abc-123-...",
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid registration data",
    "details": [{ "field": "email", "message": "Invalid email" }]
  }
}
```

| Route Prefix | Limit | Window | By | Reason |

| `/api/v1/risk` | 20 | 1 min | user | Bound risk recompute |

## Background Jobs

### Job Queue Architecture

`apps/api/src/services/satelliteJobQueue.ts` — in-process queue:

| State | Meaning |
|-------|---------|
| `PENDING` | Created, not yet picked up |
| `RUNNING` | Currently processing |
| `RETRYING` | Failed, waiting for backoff before retry |
| `COMPLETED` | Finished successfully |
| `FAILED` | Retries exhausted, will not retry |

### Retry Policy

- **Max retries**: 3 attempts
- **Backoff**: exponential (1s, 2s, 4s)
- **Retryable errors**: network errors (`ECONNREFUSED`, `ETIMEDOUT`, `ENOTFOUND`, fetch failed)
- **Non-retryable**: provider auth errors → `PROVIDER_STATE`; other errors → `STALE`

### Idempotency

- Same project cannot have two PENDING/RUNNING/RETRYING jobs at once (returns `ALREADY_RUNNING`)
- DB has unique constraint on `(sceneId, observationDate)` so satellite observation ingestion is naturally idempotent

### Reliability States (per project)

| State | Triggered When |
|-------|----------------|
| `AVAILABLE` | Has observations, latest < 30 days old |
| `PROCESSING` | Active job running |
| `NO_DATA` | Job completed but found 0 usable observations |
| `PROVIDER_ERROR` | Job failed with auth/credential issue |
| `STALE` | Last observation > 30 days old, or job failed non-retryably |

Exposed in `GET /projects/:id/satellite` response as `reliabilityState`.

### Memory Management

- Jobs older than 24h are pruned via `pruneOldJobs()` (call periodically or on startup)
- For multi-instance deployments, replace with BullMQ + Redis (the API contract stays the same)

## Audit Log Integrity

Implemented in `packages/domain/src/services/auditService.ts`:

- **Append-only**: no `update` or `delete` methods exposed
- **All writes go through `prisma.auditEvent.create`**
- **Strict validation**: Zod schema validates `actorId`, `action`, `entityType`, `entityId`
- **What is logged**: login (success + failure), logout, token refresh, user creation, role/permission changes (TODO), admin actions, report submission, report moderation, finding status changes, media uploads, project updates
- **What is NOT logged**: passwords, raw tokens (only `actorId`/`sessionId` references)
- **Protected routes**: `GET /api/v1/audit` requires `audit.read` permission
- **Database-level**: production should add a trigger that prevents UPDATE/DELETE on `audit_events` (schema-level guarantee beyond application)

### Audit Log Completeness — Audited Actions

| Action | Logged? | AuditAction enum |
|--------|---------|------------------|
| Successful login | YES | `AUTH_LOGIN` |
| Failed login (user not found) | YES | `AUTH_FAILED_LOGIN` |
| Failed login (wrong password) | YES | `AUTH_FAILED_LOGIN` |
| Logout | YES | `AUTH_LOGOUT` |
| Token refresh | YES | `AUTH_TOKEN_REFRESH` |
| Registration | YES | `USER_CREATED` |
| Report submission (public) | YES | `REPORT_SUBMITTED` |
| Report moderation | YES | `REPORT_MODERATED` |
| Report status change | YES | `REPORT_STATUS_CHANGED` |
| Report triage run | YES | `REPORT_CLAIMS_EXTRACTED` |
| Media upload | YES | `REPORT_MEDIA_UPLOADED` |
| Finding status change | (TODO) | n/a |

## AI / Satellite Cost Control

### AI Provider
- `NullAIProvider` is used as the default — does not call any external API
- When a real provider is configured, `getStatus()` reports the configuration
- Rate limit on `/api/v1/risk` and `/api/v1/analytics` (20/min/user) caps expensive compute
- Per-user keyGenerator ensures one user can't starve others

### Satellite (CDSE)
- **Rate limiter**: 280 req/min sliding window (under the 300 req/min free-tier limit)
- **Token cache**: OAuth2 token cached for `expires_in - 60s`
- **Bounded searches**: `from` defaults to 1 year before `to`; no unbounded queries
- **Idempotent ingestion**: `upsertObservation` checks `(sceneId, observationDate)` unique before insert; catches `P2002` race condition
- **Selective cloud filter**: `SATELLITE_CLOUD_THRESHOLD` defaults to 60% (avoids unusable scenes)
- **Quota error handling**: 401/403 from STAC → clear token cache, return empty array (no crash)

### Idempotency Map

| Operation | Idempotency Mechanism |
|-----------|----------------------|
| Satellite observation ingest | Unique `(sceneId, observationDate)` constraint + upsert check |
| Risk analyze | `forceNewRun` flag; otherwise returns latest run if recent |
| Report submission | New ID per request (intentional — different submissions are different reports) |
| AI triage | Mark as `PROCESSING` then re-fetch; concurrent runs handled by status check |
| Anomaly detection | Idempotent based on (projectId, ruleCode, observationDate) — see risk engine |
| Financial observation | Unique on (projectId, date, source) — natural dedup |

## PWA / Offline Safety

### Service Worker (`apps/web/public/sw.js`)

- **Cache name**: `vojas-v1` (bump to invalidate)
- **API calls**: network-first, fall back to cached response on offline
- **Static assets** (`/_next/static/`, `/icons/`, `.js`, `.css`, `.woff2`, images): cache-first
- **HTML pages**: network-first, fall back to `/offline`
- **Never caches**: POST/PUT/DELETE (mutations require online)
- **Auto-cleanup**: old caches deleted on `activate` event

### Manifest (`apps/web/public/manifest.json`)

- Name, short_name, description, theme colors
- Icons (192×192, 512×512)
- Shortcuts to Projects and Reports pages
- Display: `standalone` (installable on mobile home screen)

### Offline Form Safety

- Citizen report submission via `/report` is **not** queued offline — service worker does NOT cache POSTs
- When user submits while offline: the request fails, the form preserves user input (browser default behavior)
- User must reconnect and retry
- This is intentional: a queued report could become stale or be misinterpreted, and we cannot guarantee delivery without a server-side outbox

### Drafts

- Login forms, search forms, and citizen report forms do not auto-save drafts to localStorage
- Browser's native form persistence (back/forward cache) handles in-flight data
- Future enhancement: optional `localStorage` drafts for citizen reports (with TTL) — Phase 18+

## Staleness System

Every analytics and forecast response includes:

```typescript
{
  computedAt: Date,         // When this result was computed
  staleAfter: Date,         // Treat as stale after this
  dataFreshnessDays: number, // Days since latest contributing data
  dataQuality: 'HIGH' | 'MEDIUM' | 'LOW' | 'UNKNOWN'
}
```

### Staleness Thresholds

| Resource | Stale After | Notes |
|----------|-------------|-------|
| Project analytics (active) | 24h | Refresh on demand |
| Project analytics (completed) | 168h (7d) | Less volatile |
| Aggregated metrics | 24h | Computed fresh per request |
| Forecast (delay/cost/risk) | 7d | `validUntil` field in result |
| Risk findings | 1h | Re-analyze to refresh |
| Satellite observations | 30d | After this, `reliabilityState = STALE` |

### UI Indicators (Frontend)

- `dataFreshnessDays > 7` → show "STALE" badge
- `dataQuality === 'LOW'` or `'UNKNOWN'` → show "LOW CONFIDENCE" badge
- Forecast `dataFreshness === 'STALE'` → warn user in red
- For complete UI details, see `apps/web/src/components/StalenessIndicator.tsx`

## Data Consistency

### Cross-Entity Consistency Rules

| Event | Cascade |
|-------|---------|
| Project status changes | `riskEngine.analyze()` should be re-run (manual trigger today) |
| Satellite observation added | `changeAnalysisEngine` can be re-run to update comparisons |
| Report submitted | AI triage should be triggered (`POST /reports/:id/triage`) |
| Finding status changed | Risk event created (handled in `PATCH /findings/:id/status`) |
| Anomaly created | `riskFindings` linked by `findingId` |
| User role changed | Audit log entry written (TODO: full role-change audit) |

### Transaction Safety

- All critical multi-step writes use Prisma `$transaction` (e.g. report submission creates Report + AnonymousReportAccess + ReportStatusLog)
- Risk finding status changes write a `riskEvent` in the same logical operation (separate insert; if the event insert fails, the status change still succeeds — see "Consistency Trade-offs")

### Known Trade-offs

- **Risk engine does not auto-trigger** on data changes. Operators manually call `POST /projects/:id/risk/analyze`. Phase 18: implement event-driven triggers.
- **Change analysis is on-demand**, not continuous. Run on `POST /projects/:id/satellite/sync` or manually.
- **Anomaly → Finding link** is one-way (Anomaly has `findingId`, Finding has `signalIds`). Update one side and the other may go stale.

### Idempotency in Service Layer

- `selectBestObservation` always picks lowest cloud cover (deterministic)
- `syncProjectSatellite` is safe to re-run (idempotent ingestion)
- `auditEvent.create` uses unique IDs (CUID) so duplicates are impossible
- `report.create` allows duplicates by design (different reports from different sources)

## Migration Safety

See `docs/PRODUCTION_READINESS.md` and `docs/DATABASE.md` for full details.

Key points:
- All migrations use `prisma migrate dev` (version-controlled)
- Foreign keys have explicit `onDelete` rules
- Destructive changes follow 3-step deploy: add nullable → backfill → constraint
- Rollback = write a forward migration that reverts the change

## Quick Reference: Common Operations

### Check if the API is healthy
```bash
curl -s https://api.vojas.in/health    # Liveness
curl -s https://api.vojas.in/ready     # Readiness (DB included)
```

### Find a failed request
```bash
# Server-side: grep logs for requestId
grep '"requestId":"abc-123"' app.log

# Client-side: X-Request-Id header is set on every response
curl -i https://api.vojas.in/health | grep X-Request-Id
```

### Trigger a satellite sync
```bash
# Submit a job
curl -X POST -H "Authorization: Bearer $TOKEN" \
     https://api.vojas.in/api/v1/projects/<id>/satellite/sync

# Check job status
curl -H "Authorization: Bearer $TOKEN" \
     https://api.vojas.in/api/v1/projects/<id>/satellite/jobs/<jobId>
```

### Rotate the audit log
```bash
# Audit log grows unbounded; archive and prune periodically:
psql -c "COPY (SELECT * FROM audit_events WHERE timestamp < NOW() - INTERVAL '1 year') \
         TO '/tmp/audit_archive.csv' WITH CSV HEADER"
psql -c "DELETE FROM audit_events WHERE timestamp < NOW() - INTERVAL '1 year'"
```
